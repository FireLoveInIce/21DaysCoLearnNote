# LI.FI 本地机会监控面板

一个不连接钱包、不签名、不执行交易的静态监控页面。它会请求两次同链 LI.FI Quote：

```text
计价币 → 中间币 → 计价币
```

页面以两段 `toAmountMin` 作为保守返还值，再扣除能够折算为计价币的 Gas 和未包含费用，计算预计净收益与 ROI。

## 本地运行

在仓库根目录执行：

```powershell
cd project/monitor
python -m http.server 4173
```

然后访问 <http://localhost:4173>。

也可以直接打开 `index.html`，但推荐通过本地 HTTP 服务运行，以获得一致的浏览器行为。

## 功能

- 动态读取 LI.FI 支持的 Token，并内置常用 Token 作为离线回退；
- 配置链、计价币、中间币、测试金额、滑点、阈值与轮询间隔；
- 正向与反向 Quote 串行验证；
- 使用 `toAmountMin` 计算保守的闭环结果；
- 展示 Provider、费用、Gas、耗时和报价状态；
- 自动轮询、页面隐藏时暂停、请求预算保护；
- 浏览器本地保存配置和最近 80 条扫描历史；
- 无构建步骤，可直接部署到 GitHub Pages。

## GitHub Pages 部署

仓库根目录已经包含 `.github/workflows/monitor-pages.yml`：

1. 将代码推送到 GitHub 的 `main` 分支；
2. 打开仓库 `Settings → Pages`；
3. 在 `Build and deployment` 中将 Source 选择为 `GitHub Actions`；
4. 手动运行 `Deploy LI.FI monitor to GitHub Pages`，或修改 `project/monitor/**` 后推送。

工作流会直接发布 `project/monitor`，不需要 Node.js 或构建产物。

## API 与限流

静态页面不会保存或传输 API Key。公共 Quote 接口当前额度较低，每轮扫描需要两次请求；页面默认每 240 秒扫描一次，并维护最近两小时的本地请求计数。这个计数只代表当前浏览器，LI.FI 服务端额度仍可能受同一出口 IP 的其他请求影响。

不要把 LI.FI API Key 放到静态页面或提交到 GitHub。需要更高额度时，应增加后端代理并在服务端保管密钥。

## 结果边界

- Quote 是短时有效的估算，不保证最终成交；
- 快速报价默认跳过余额模拟，Gas 可能不够精确；
- 报价盈利不代表两笔交易能够原子执行；
- LI.FI、DEX、Solver、Gas、滑点和价格冲击均可能压缩收益；
- 当前版本适合机会观察和数据积累，不适合直接驱动真实资金。

## 设计与开发过程

### 为什么采用纯静态页面

第一版的目标是本地测试、公开查看和快速迭代，不需要账户、数据库或交易签名。原生 HTML、CSS 和 JavaScript 可以直接部署到 GitHub Pages，没有依赖安装、构建产物和服务器费用，也避免在前端引入不必要的复杂度。

页面只通过 HTTPS 请求 LI.FI Public API，配置和扫描历史保存在浏览器 `localStorage` 中。由于静态页面中的任何内容都对访问者可见，因此设计上不接受也不保存 LI.FI API Key。

### Token 选择与自定义中间币

- 计价币和中间币的选择项同时显示 Ticker、名称和完整合约地址；选择框下方也会固定展示当前合约地址，避免仅凭同名 Ticker 误选资产。
- LI.FI 会在选定的两个 Token 之间自动寻找路由，用户无需人工指定 DEX 或逐跳路径。
- 如果目标中间币不在 LI.FI Token 列表中，可以展开“手动添加中间币”，填写当前链上的合约地址、Ticker、Decimals 和可选名称。
- 自定义中间币按链保存在当前浏览器的 `localStorage` 中，不会提交到仓库或上传到本项目的服务器。
- 合约地址和 Decimals 填错会导致金额解析错误或 Quote 失败；添加前必须通过对应链的区块浏览器核对。手动添加只代表允许尝试报价，不保证 LI.FI 存在可用流动性或路由。

### 扫描逻辑

每轮扫描串行执行两个 Quote：

```text
输入计价币
  → 正向 Quote 的 toAmountMin
  → 作为反向 Quote 的 fromAmount
  → 反向 Quote 的 toAmountMin
  → 扣除可折算 Gas 和未包含费用
  → 计算净收益与 ROI
```

使用 `toAmountMin` 而不是 `toAmount`，是为了避免用乐观输出夸大机会。`feeCosts` 中已经包含在输出里的费用只用于展示，只有明确标记为未包含的费用才会再次从利润中扣除。

## 开发中的问题与挑战

### LI.FI Quote 不适合作为高频行情流

Quote 是短时有效的可执行报价，不是 WebSocket 行情。多链、多币种、多金额和多 Provider 会让请求数快速增长。当前版本先限制为单个往返交易对，未来应由 Alchemy WebSocket 或链上池状态先产生候选，再调用 LI.FI 做精算。

### 公共接口限流

一轮往返需要两次 `/quote`。无密钥公共额度无法支持秒级持续轮询，因此默认间隔为 240 秒，并在本地维护最近两小时的 70 次安全预算。该预算只能保护当前浏览器，不能代表同一出口 IP 的完整服务端额度。

### GitHub Pages 没有后端

静态部署无法隐藏密钥或代理请求。开发时实际验证了 LI.FI Quote 和 Token 接口的浏览器跨域响应；当前功能可以直接运行。需要更高额度、统一缓存或多用户服务时，必须增加独立后端，并只在服务端保存 API Key。

### Token 列表体积

单链可能包含近千个 Token。页面采用动态读取、常用资产优先排序、本地缓存和内置回退，以兼顾完整性与接口失败时的可用性。

### Gas 与费用归一化

最终利润以计价币表达，但 Gas 以链上原生币支付。页面使用 Quote 提供的美元价格，将两段 Gas 和未包含费用转换为计价币。若 LI.FI 没有返回可靠价格，页面会明确提示净利润没有完整扣除 Gas。

### 顺序报价不是原子套利

两次 Quote 之间池状态可能变化，第一笔成交后第二笔也可能失败。因此页面将结果称为“候选机会”，而不是“可执行套利”。真实执行还需要同一区块模拟、原子执行合约以及交易末尾的最低利润检查。

### 报价有效期

Quote 很快会失效。页面持续显示报价年龄，超过 60 秒后标记为历史参考；自动监控在标签页隐藏时暂缓，避免浪费额度获取无人查看的旧报价。

## 验证记录

- JavaScript 静态语法检查通过；
- HTML 必需元素及重复 ID 检查通过；
- 本地 HTTP 服务可以正常返回页面和脚本；
- LI.FI Token 接口在 Base 返回 976 个 Token；
- Base 上 USDC → WETH → USDC 双向 Quote 成功；
- 正反向 Quote 均返回 Provider、`toAmountMin`、Gas、费用和计价币价格；
- LI.FI 响应包含允许 GitHub Pages 浏览器调用的跨域头。
