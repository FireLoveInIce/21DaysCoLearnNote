# Day 01 学习记录：Uniswap 演进与 V2 AMM 基础

## 今日目标

- 建立 Uniswap V1—V4 的整体演进视图。
- 理解 Uniswap V2 的恒定乘积模型 `x * y = k`。
- 能够说明价格、流动性、滑点、价格影响和手续费之间的关系。
- 理解 V2 中 `Factory`、`Pair`、`Router` 的职责与一次 Swap 的基本调用链。

## 一、Uniswap V1—V4 的演进

| 版本 | 主要解决的问题 | 核心变化 | 新的取舍或风险 |
| --- | --- | --- | --- |
| V1 | 验证 AMM 和无需许可交易能否工作 | 所有池均为 `ETH/ERC-20`，使用恒定乘积做市 | 任意两种 ERC-20 交易必须经过 ETH 中转，需要两次交易并支付两次手续费 |
| V2 | 支持更灵活的交易对和更可靠的链上价格 | 支持任意 `ERC-20/ERC-20` 交易对；引入累计价格/TWAP、闪电交换；拆分 Core 与 Periphery | 流动性仍均匀分布在 `(0, +∞)`，大量资金在当前价格附近之外闲置 |
| V3 | 提高资金效率，适配不同波动性的资产 | 集中流动性、Tick、多个费率档位、改进的 TWAP；LP 仓位不再天然同质化，通常用 NFT 表示 | LP 需要选择价格区间；价格离开区间后停止赚取手续费，管理复杂度和主动管理需求上升 |
| V4 | 降低建池及复杂操作成本，并允许开发者扩展池逻辑 | 单例 `PoolManager`、Hooks、闪电记账、原生 ETH、动态费率和自定义记账 | Hook 引入额外代码与安全边界；不同 Hook 会造成池行为差异 |

演进主线可以概括为：

> V1 验证 AMM → V2 完善通用交易与可组合性 → V3 提高资金效率 → V4 将 AMM 变成可扩展的流动性基础设施。

V3、V4 并没有简单废弃恒定乘积思想。V3 将流动性限制在 LP 选择的价格区间内；V4 的基础池延续集中流动性，同时允许 Hook 在生命周期节点加入自定义逻辑。

## 二、V2 中 LP、交易者和套利者的角色

### 1. 流动性提供者（LP）

LP 按池中当前比例存入两种资产，获得代表池份额的 LP Token。交易者每次 Swap 支付的 0.3% 输入手续费先留在池中，使 `k` 随交易逐渐增长，LP 在移除流动性时按份额取回资产和累积手续费。若治理开启 V2 协议费，协议会在增减流动性时通过铸造 LP Token 捕获一部分增长，并非额外向交易者收费。

LP 承担的主要风险包括：

- 两种资产相对价格变化造成的无常损失；
- 智能合约和代币本身的风险；
- 低交易量导致手续费不足以覆盖风险；
- 极端行情下池中资产结构向表现较弱的一侧倾斜。

### 2. 交易者

交易者用一种资产换取另一种资产。成交结果由储备量、输入数量和手续费共同决定。交易相对池子越大，推动储备比例变化越明显，价格影响越大。

交易者通常通过 Router 设置：

- 输入数量或目标输出数量；
- 交易路径 `path`；
- 最小可接受输出 `amountOutMin` 或最大可接受输入；
- 截止时间 `deadline`。

这些参数是交易者的执行保护，不会保证交易一定成功。

### 3. 套利者

外部市场价格变化后，V2 池内价格不会自动更新。套利者发现池内外价差后，与价格偏低的一侧买入、向价格偏高的一侧卖出，改变池内储备比例，使池价重新接近外部市场价。

套利的作用是把外部价格信息带入池中，但通常不会把价差压到绝对为零。只要剩余价差不足以覆盖 LP 手续费、Gas、滑点、MEV 和失败风险，继续套利就不再有利可图。

三类角色形成的循环是：交易者产生交易和手续费，LP 提供成交深度，套利者使池内价格持续靠近外部市场价格。

## 三、恒定乘积、价格与成交结果

### 1. 不考虑手续费的基本模型

设池中两种代币储备量为 `x` 和 `y`：

```text
x * y = k
```

若交易者输入 `Δx`，获得 `Δy`，交换后应满足：

```text
(x + Δx) * (y - Δy) = k
```

因此：

```text
Δy = y * Δx / (x + Δx)
```

若把 `x` 看作 token X，把 `y` 看作 token Y，则交易前的边际价格为：

```text
1 X 的 Y 计价 = y / x
1 Y 的 X 计价 = x / y
```

这里必须先说明价格方向，单写 `x / y` 容易把报价方向写反；还必须先按各 Token 的 `decimals` 把链上整数换算成人类可读数量。

### 2. 加入 V2 的 0.3% 输入手续费

有效输入为：

```text
Δx_eff = Δx * 997 / 1000
```

精确输入时的输出量为：

```text
amountOut = reserveOut * amountIn * 997
          / (reserveIn * 1000 + amountIn * 997)
```

Solidity 使用整数除法，结果向下取整。链下计算若使用浮点数，可能与合约结果出现微小偏差；构造交易时应使用整数或高精度十进制。

### 3. 手算示例

假设池中有 `100 ETH` 和 `200,000 USDC`，暂不考虑代币精度差异：

```text
交易前边际价格 = 200,000 / 100 = 2,000 USDC/ETH
输入             = 1 ETH
有效输入         = 1 * 0.997 = 0.997 ETH
输出             = 200,000 * 0.997 / (100 + 0.997)
                 ≈ 1,974.3161 USDC
平均成交价格     ≈ 1,974.3161 USDC/ETH
```

交易完成后的实际储备约为：

```text
ETH   = 101
USDC  = 198,025.6839
池内边际价格 ≈ 1,960.6503 USDC/ETH
```

相对交易前 `2,000 USDC/ETH`，平均成交报价下降约 `1.284%`。这部分总差异同时包含 0.3% 手续费和沿曲线成交造成的价格影响，不能全部称为手续费。

## 四、流动性、价格影响与滑点的区别

| 概念 | 含义 | 关键影响因素 |
| --- | --- | --- |
| 流动性 | 池在某一价格附近承接交易的深度 | 储备规模；V3/V4 中还取决于当前 Tick 附近的活跃流动性 |
| 价格影响（Price Impact） | 当前交易本身改变池储备比例，导致成交均价偏离交易前边际价格 | 交易量相对池深的比例；交易越大，影响越大 |
| 滑点（Slippage） | 从报价到上链成交期间，由状态变化导致的预期成交与实际成交差异；界面中也常用“滑点容忍度”表示用户允许的最大偏差 | 报价延迟、其他交易、价格波动、抢跑与交易排序 |
| 手续费 | 协议按输入量扣取的费用，V2 默认是 0.3% | 输入量和协议费率 |

严格来说，价格影响是当前交易在给定池状态下可预先计算的曲线结果；滑点是报价之后池状态继续变化带来的额外偏差。实际产品界面有时会混用两者，因此分析交易时应明确采用哪一定义。

## 五、储备量变化如何影响报价

- `reserveIn` 增加、`reserveOut` 不变时，同样输入可获得的输出减少。
- `reserveOut` 增加、`reserveIn` 不变时，同样输入可获得的输出增多。
- 两边储备按相同比例扩大时，现货价格不变，但同规模交易的价格影响降低。
- Swap 会改变两边储备比例，因此沿曲线连续成交，而不是所有数量都按交易前现货价成交。
- 手续费留在池中，所以实际交易后，经手续费调整检查的不变量不下降，而未调整的储备乘积通常略有增加。

注意：`getReserves()` 返回 `reserve0`、`reserve1` 和 `blockTimestampLast`。第三个值是最近一次储备更新的时间戳，不是区块高度。区块号需通过 RPC 另行读取，并应将“报价所用储备”和“查询区块号”绑定记录，才能复现结果。

## 六、Factory、Pair、Router 如何协作

### 1. Factory：注册和创建 Pair

- `getPair(tokenA, tokenB)`：查询交易对地址；不存在时返回零地址。
- `createPair(tokenA, tokenB)`：部署并登记新的 Pair。
- Factory 保证同一组排序后的 Token 只有一个官方 V2 Pair。

### 2. Pair：保管资产并执行核心规则

- 保存 `token0`、`token1` 和储备量。
- 发行/销毁 LP Token，处理 `mint`、`burn`。
- 在 `swap` 中转出代币、根据余额差计算实际输入、扣除手续费后检查恒定乘积约束。
- 更新储备和累计价格，发出 `Swap`、`Sync`、`Mint`、`Burn` 事件。

Pair 的 `swap` 是底层接口。它要求调用方正确安排代币转入、输出量和接收地址，普通用户一般不应绕过 Router 直接调用。

### 3. Router：计算和编排用户操作

- `getAmountsOut(amountIn, path)`：根据各 Pair 当前储备逐跳计算预期输出。
- `swapExactTokensForTokens(...)`：检查 deadline 和最小输出，通过 `transferFrom` 把输入代币送入首个 Pair，并逐跳调用 Pair。
- Router 不持久保存流动性，是可替换的外围合约；资产和恒定乘积规则位于 Pair。

一次精确输入交易的简化调用链：

```text
用户 approve Router
    ↓
用户调用 Router.swapExactTokensForTokens
    ↓
Router 读取 Pair 储备并计算逐跳 amounts
    ↓
Router.transferFrom：用户 → 第一个 Pair
    ↓
Router 调用 Pair.swap
    ↓
Pair 转出 token、计算实际输入、校验 K、更新储备
    ↓
多跳时输出直接进入下一个 Pair；最后一跳转给接收者
    ↓
Pair 发出 Swap 和 Sync 事件
```

## 七、重点接口与事件速查

| 接口/事件 | 用途 | 注意事项 |
| --- | --- | --- |
| `Factory.getPair` | 获取 Pair 地址 | 先检查是否为零地址 |
| `Factory.createPair` | 创建新 Pair | 任何人均可调用，但同一 Token 组合不能重复创建 |
| `Pair.token0/token1` | 确定储备量对应的 Token | 由地址排序，不等于调用时传参顺序 |
| `Pair.getReserves` | 读取储备及最近更新时间 | 储备是原始整数；第三个返回值不是区块号 |
| `Pair.swap` | 执行底层交换/闪电交换 | 低级接口，需要调用者做好安全校验 |
| `Router.getAmountsOut` | 计算一条路径的预期输出 | 只基于调用时储备，不是价格承诺，也不是外部预言机 |
| `Router.swapExactTokensForTokens` | 固定输入进行交易 | 需提前授权，并合理设置 `amountOutMin` 和 `deadline` |
| `Swap` | 记录实际输入、输出、调用者和接收者 | 解析时需结合 `token0/token1` 判断方向 |
| `Sync` | 记录更新后的 `reserve0/reserve1` | 同一笔 Swap 中通常紧随储备更新出现 |
| `Mint` | 记录加入流动性的两种 Token 数量 | LP Token 的接收者需结合交易调用分析 |
| `Burn` | 记录移除流动性返还的数量和接收者 | 不应误判为普通 Swap |

## 八、问题总结

1. **各版本解决了什么问题？** V1 验证无需许可 AMM；V2 支持任意 ERC-20 对并完善预言机、闪电交换和合约分层；V3 用集中流动性和多费率提高资金效率；V4 用单例、Hook 和闪电记账提高可扩展性与组合效率。
2. **三类参与者分别做什么？** LP 提供库存并赚取手续费，交易者消费流动性完成兑换，套利者利用价差交易并把池价推回外部市场附近。
3. **储备量如何决定成交？** 储备比例决定交易前边际价格，恒定乘积曲线决定不同交易量的输出，手续费减少有效输入；交易相对池越大，价格影响越明显。
4. **三类合约怎样协作？** Factory 创建和索引 Pair，Pair 保管资金并强制执行不变量，Router 负责报价、转账、多跳编排和用户保护参数。

## 今日复盘

### 最重要的三个收获

1. V2 的报价不是订单簿报价，而是由储备量和 `x * y = k` 曲线实时计算；交易本身会改变后续价格。
2. LP、交易者和套利者构成闭环：LP 提供深度，交易者支付手续费，套利者让池价接近外部市场。
3. V2 的职责边界清晰：Factory 管注册，Pair 管资产和不变量，Router 管路径与用户交互。

### 仍需深入理解的地方

- 手续费、价格影响、滑点和 MEV 在真实交易结果中的拆分方法。
- TWAP 累计价格的读取、时间窗口选择及抗操纵边界。
- 闪电交换回调以及 Pair “先转出、后校验”的原子性保证。
- 无常损失与手续费收益在不同波动率、交易量下的盈亏平衡。

### 明日需要验证的假设

- 链下使用整数公式计算的 `amountOut` 应与同区块 `getAmountsOut()` 完全一致。
- 只依赖 `Swap` 事件可以恢复交易方向和数量，但要结合 `token0/token1`、代币精度及多跳上下文。
- 构建 V2 监控的最小链上数据至少包括 Pair 地址、Token 元数据、储备、区块号和相关事件日志。
