# Day 14 学习记录：用 LI.FI Quote 构建套利机会监控面板

## 今日目标

- 理解 LI.FI 在多链交易基础设施中的定位与能力边界。
- 判断 LI.FI Quote 是否适合作为套利监控和执行依据。
- 将“价格差异”转化为包含费用、Gas、滑点和时效性的结构化信号。
- 初始化一个可在本地运行、可免费部署到 GitHub Pages 的监控面板。

## 一、LI.FI 能提供什么

LI.FI 不是单一跨链桥，而是一层多链流动性路由与执行基础设施。它把 Bridge、DEX Aggregator、Solver、收益协议和多步合约调用统一到 API、SDK、Widget 和 Composer 中。

与本项目直接相关的能力包括：

- 同链兑换和跨链兑换；
- 根据价格、Gas、速度和成功率选择路线；
- 返回保守最低到账量 `toAmountMin`；
- 返回费用 `feeCosts`、Gas `gasCosts` 和预计执行时间；
- 返回可签名的 `transactionRequest`；
- 查询支持的链、Token、Bridge 和 Exchange；
- 追踪跨链交易状态。

LI.FI 更适合充当“可执行报价与路线验证层”，而不是区块级、交易级或 mempool 级的高频行情源。

## 二、能否自己合约执行并避免 LI.FI 费用

需要区分两种情况。

### 1. 自有合约转发 LI.FI Quote

Quote 返回的 `transactionRequest.to` 通常是 LI.FI Diamond 合约，`data` 已经编码了路线与费用步骤。自己的 Executor 合约可以在满足余额、授权、原生币转发和地址一致性要求时调用它，但这不会去除 LI.FI 的费用。

主要原因：

- `feeCollection` 已经包含在执行路线中；
- 输出金额与 `toAmountMin` 已按照完整路线计算；
- 随意删除或修改费用步骤可能导致校验失败、交易回滚或退款异常；
- 自有合约多包一层调用还可能增加 Gas。

### 2. 观察 LI.FI 路线，再直接调用底层协议

技术上可以重新集成底层 DEX、Bridge 或 Solver，但这已经不是在执行 LI.FI Quote，而是在自行构建一个简化聚合器。需要独立处理：

- 底层协议询价与 calldata；
- Token 授权；
- 滑点与 Price Impact；
- Bridge 消息和退款；
- 交易模拟、失败恢复和状态追踪；
- LI.FI 商业 API 条款中的价格模型与使用限制。

因此，本阶段不以“绕过费用”为目标，只使用 LI.FI 进行研究和报价验证。

## 三、监控方案是否可行

可行，但不能把 LI.FI `/quote` 当作无限调用的实时价格流。

推荐结构：

```text
Alchemy WebSocket / 链上 Swap 事件
                 ↓
          候选机会生成器
                 ↓
           LI.FI Quote 验证
                 ↓
      费用与 Gas 统一折算、阈值判断
                 ↓
        本地监控页面、历史与告警
```

当前版本先完成 LI.FI Quote 验证和监控页面。后续再复用 Day 12 的 Alchemy WebSocket 采集器增加高频候选发现，以减少 Quote 请求数量。

## 四、第一版信号模型

监控同一条链上的往返路线：

```text
计价币 → 中间币 → 计价币
```

执行过程：

1. 将测试金额换算为计价币最小单位。
2. 请求正向 Quote。
3. 使用正向 `toAmountMin` 作为反向 Quote 的输入。
4. 取得反向 `toAmountMin` 作为保守最终返还。
5. 汇总两段 `feeCosts` 和 `gasCosts`。
6. 检查 `feeCosts[].included`，避免重复扣费。
7. 将 Gas 和未包含费用折算为计价币。
8. 计算净收益和 ROI，并与机会阈值比较。

保守计算方式：

```text
预计净收益
= 最终 toAmountMin
- 初始投入
- 可折算 Gas
- 未包含在到账量中的费用
```

信号分为：

- 等待扫描；
- 未达阈值；
- 候选机会；
- 扫描失败。

“候选机会”只代表两次顺序 Quote 在当前估算下达到阈值，不代表可以无风险执行。

## 五、实现结果

代码位于 `project/monitor/`，采用原生 HTML、CSS 和 JavaScript，不依赖 Node.js 构建，因此可以直接通过 GitHub Pages 发布。

已实现：

- Base、Arbitrum、Optimism、Ethereum 和 Polygon；
- LI.FI Token 动态列表与内置常用 Token 回退；
- 链、Token、金额、滑点、阈值、路由偏好和轮询间隔配置；
- 正向与反向 Quote；
- `toAmountMin`、费用、Gas、净收益和 ROI 展示；
- 自动轮询与页面隐藏暂停；
- 最近两小时本地请求预算保护；
- 路线明细、历史表格、ROI 趋势和活动日志；
- 浏览器本地保存配置及最近 80 条历史；
- 响应式布局；
- GitHub Actions 自动发布 GitHub Pages。

## 六、开发中的问题与挑战

### 1. Quote 不是行情接口

每次扫描需要正反两个 Quote。若继续扩展为多链、多币种、多金额和多 Provider，调用量会快速呈乘法增长。因此需要让链上事件先筛选候选，再使用 Quote 做精算。

### 2. 公共 API 限流

无 API Key 时 Quote 额度很低。页面默认 240 秒轮询一次，并在浏览器记录最近两小时请求次数，达到安全预算后停止请求。静态页面不能安全保存 API Key；若以后需要更高额度，应增加服务端代理。

### 3. 静态页面跨域

GitHub Pages 只能提供静态文件，无法通过同域后端转发请求。开发时实际检查了 LI.FI Quote 和 Token 接口，响应包含允许浏览器访问的跨域头，因此可以直接从页面调用。

### 4. Token 数量与回退

Base 的 LI.FI Token 接口实际返回近千个 Token。页面需要在完整性、选择性能和常用资产可见性之间权衡，因此采用“动态列表 + 常用 Token 优先排序 + 缓存/内置回退”。

### 5. 费用不能重复扣除

部分协议费用已经包含在 `toAmountMin` 中。如果再次从最终金额中扣除，会低估结果。实现中只对 `included === false` 的费用进行额外折算，所有费用仍单独展示。

### 6. Gas 折算

Gas 通常以原生币支付，而利润以计价币表达。页面优先使用 Quote 中的 Token 美元价格或 `fromAmountUSD` 反推计价币价格，再把 Gas 转换为计价币。缺少可靠价格时会明确提示结果尚未完整扣除 Gas。

### 7. 非原子执行

两次 Quote 是顺序估算。第一笔交易完成后，池状态、Gas 和第二段报价都可能变化。当前页面只做观察；真实执行前还需要同一区块模拟、原子合约和最低利润检查。

### 8. Quote 时效

Quote 通常只有很短的有效窗口。页面显示报价年龄，超过 60 秒即标记为历史参考，避免把旧报价当成实时机会。

## 七、真实接口验证

开发时使用 Base 上的 USDC → WETH → USDC 做了一轮双向 Quote：

- 正向与反向接口均成功返回；
- Provider 均返回为 OKX；
- Token 价格、Gas、费用与 `toAmountMin` 字段均可读取；
- 示例 100 USDC 的保守最终返还低于初始投入，符合手续费和滑点预期；
- Quote 与 Token 接口均允许浏览器跨域访问。

这个结果也说明：看到价格差异不等于存在净套利，费用精算是信号生成不可缺少的一步。

## 八、风险与边界

- 页面不连接钱包、不签名、不执行交易；
- 不应在静态页面或 GitHub 中加入私钥、助记词和 LI.FI API Key；
- Quote 不保证最终成交；
- 快速报价跳过余额模拟，Gas 可能不够精确；
- LI.FI、DEX、Solver、Gas、滑点、价格冲击和 MEV 都可能改变结果；
- GitHub Pages 版本只用于学习、测试和查看。
